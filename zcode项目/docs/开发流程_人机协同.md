# 人机协同开发流程

> 版本：v1.0 · 2026-09-19
> 目的：让"我提需求 → AI 改代码"这件事**可预测、可回溯、不出意外**。
> 配套：[游戏设计文档](游戏设计文档.md) · [测试用例](测试用例.md)

---

## 一、核心原则（三条）

1. **文档是唯一真相。** 游戏行为与 GDD 不符 = bug，要么改代码、要么改文档，**不允许沉默地不一致**。
2. **先改文档，再改代码。** 需求确认后，先更新 GDD 里"期望行为"和测试用例里"验收项"，让双方对"做对了"有一致定义，然后动手。
3. **先验证再交付。** 任何代码改动，交付前必须跑过 `run_all_tests.py`；跑不了的（视觉/手感）要在文档里标明"未验证"。

---

## 二、标准变更流程（6 步）

```
1. 提需求
   我按模板提（见第五节）。AI 若发现描述含糊，先问清楚再动手。

2. 对齐文档（改代码之前）
   ├─ 更新 docs/游戏设计文档.md 的「期望行为」
   └─ 更新 docs/测试用例.md 的「验收项」
   → 这一步产出的是"我们对齐了什么"，不是可选项

3. 定位影响面
   AI 列出：要改哪几个文件、会不会影响其他关卡/机制（见第三节映射表）

4. 改代码 + 加测试
   新机制必须配 test_*.gd 或 probe_*.gd；修 bug 必须在测试用例文档登记回归要点

5. 验证
   ├─ 自动化：python tools/run_all_tests.py   （必须 24/24 通过）
   └─ 手工：按测试用例文档的清单过一遍（手感/演出/视觉）

6. 提交
   git commit（规范见第四节）→ push
   并在 GDD 的「变更记录」追加一行
```

> **反模式**：不要"我先改代码，文档以后补"。经验是补不上，最后变成"代码里有规则但没人知道"，就会出现"空格键到底干嘛的""咆哮为什么要选人"这类问题。

## 三、变更类型 → 影响文件映射

**改东西前先看这张表，避免"改了一个地方，另一个地方没跟上"。**

| 想改什么 | 代码位置 | 同步文档 |
|---|---|---|
| 单位血量/攻防/移动 | `data/units.json` | GDD §6 |
| 关卡军令（胜利条件） | `data/chapters/chapterN.json` 的 `stages` | GDD §4 |
| 新增胜利条件类型 | `scripts/core/objectives.gd` + `battle.gd:_build_objective_ctx()` | 原著速查 §3 |
| 绝技效果/数值 | `scripts/entities/skills.gd` + `scripts/core/combat.gd` | GDD §3 |
| 关卡剧情对白 | `data/dialogs/chapterN_dialogs.json` | GDD §4 |
| 按键与操作手感 | `scripts/battle.gd` 的 `_input()` / `_handle_click()` | **GDD §2.2 按键表** |
| 回合流程 | `battle.gd` 的 `_after_action` / `_end_player_turn` / `_begin_player_turn` | **GDD §2.1** |
| 面板显示 | `battle.gd:_update_dashboard()` / `_update_chapter_objectives()` | GDD §2.1 |
| 抽奖/声望经济 | `scripts/systems/lottery.gd` / `save.gd` | GDD §5 |
| 将缘（羁绊） | `scripts/systems/bonds.gd` | GDD §3.5 |
| 立绘/单位贴图接入 | `assets/{portraits,units}/` + `scripts/ui/*.gd` | 美术指南 |

**连带检查清单**（改完自问）：
- 这个改动会不会影响另外三关？（四关共用同一套战斗代码）
- 面板/提示文案要不要同步改？（玩家从面板获取规则）
- 旧测试的断言还成立吗？（历史上出现过"测试期待旧行为"导致的假失败）

## 四、提交规范

```
<type>(<scope>): <中文一句话说清做了什么>

type: feat 新功能 | fix 修 bug | docs 文档 | test 测试 | art 美术 | refactor 重构
scope: battle / skills / objectives / art / docs ...
```

示例：
```
fix(battle): 全屏进关卡画面挤到左下角——不再强制改窗口尺寸
feat(objectives): 第三关改为招降许褚（打到三成血逼其归顺）
```

**一次提交只做一件事**。修 bug 别顺手重构，混在一起出了问题不好回滚。

## 五、怎么提需求（模板）

用这个格式，我就能准确执行，不用来回问：

```
【需求】一句话说清要什么
【触发场景】玩家做什么 → 现在怎么样 → 期望怎么样
【验收标准】怎么算做对了（可观察的现象）
【边界】不要动什么 / 不能影响什么
```

**例子（好）：**
> 【需求】张飞咆哮不用点目标
> 【触发场景】选中张飞 → 点「咆哮」→ 现在会进入"选择目标"状态，必须点一个敌人 → 期望直接开始喊字
> 【验收标准】点咆哮后立刻出现"燕人张飞在此（6/14 字）"提示，可连点加字
> 【边界】关羽的龙斩仍需要指定方向，不要改成不用选

**例子（差）：**
> "咆哮用起来不顺手" ← 我不知道你指的是选目标、还是字数、还是 CD

## 六、当前项目已知的技术约定（避免重复踩坑）

| 约定 | 说明 |
|---|---|
| GDScript 严格模式 | 项目开了"警告即错误"：`var x := 某Variant` 会直接编译失败，必须显式标类型 |
| 场景切换传参 | 用 `BattleScript.chapter_id`（static var）传关卡号，不要用 `get_tree().current_scene` 反射 |
| 新增 PNG 必须导入 | 跑一次 `--headless --import`，否则 `ResourceLoader.exists()` 返回 false |
| `.gitignore` 白名单 | `*.png` 是全局忽略的，美术资产靠 `!**/assets/{portraits,units,tiles}/*.png` 放行 |
| 存档字段 | 新增字段必须同时加进 `SaveCore.new_state()`，否则会被 `load_state()` 丢弃 |
| 测试命名 | `test_*` / `probe_*` 才会被全量回归自动发现 |
